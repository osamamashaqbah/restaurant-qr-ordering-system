نقاط قوة تذكرها بثقة

كيف فكرنا بالأمان وصحة البيانات؟

لا تثق بالعميل

السعر والإجمالي يعاد حسابهما في Postgres، وليس من قيم Angular.

أقل صلاحية

الكاشير يغير توفر الصنف فقط، ولا يستطيع تعديل السعر أو الصورة أو الاسم.

الدفاع على طبقات

Guard في Angular للتجربة، Policy في ASP.NET، وRLS/Functions في Postgres للحماية الحقيقية.

لا تكشف بيانات شخصية

التتبع يستخدم token عشوائياً وhash، ويعيد حالة الطلب وline items الآمنة فقط.

لا تكرر الطلب

Idempotency-Key وrequest hash يعالجان retry بعد انقطاع الشبكة.

احمِ الخدمة

CORS يحدد origins المسموحة وrate limiting يحد إنشاء الطلبات العامة.

كيف أشرح المشروع بسرعة؟

هذا نظام طلبات مطعم باستخدام QR واحد. الواجهة مبنية بـ Angular 22، والـ backend بـ ASP.NET Core 8 Web API، والبيانات والهوية على Supabase Postgres وAuth. الزبون يرى القائمة ويضع الطلب، والـ API يعيد تسعير العناصر من قاعدة البيانات ويصدر tracking token آمناً. الموظفون يدخلون بـ JWT، وكل دور له لوحة وصلاحيات محددة للمطبخ والكاشير والإدارة. طبقت الحماية على أكثر من طبقة باستخدام validation وpolicies وRLS، وأضفت idempotency لمنع تكرار الطلبات عند retry. اختبرت المنطق بـ unit/API tests والرحلات الأساسية بـ Playwright.

للمراجعة العملية: شغّل npm --prefix frontend start ثم افتح /guide. وللتحقق الكامل شغّل dotnet test RestaurantQrOrdering.sln وnpm run test:e2e من جذر المشروع.
